# Проверка заказов маркетплейса

Это тестовое задание по обработке выгрузки заказов. За основу я взял выданный
черновой скрипт и дорабатывал его постепенно, не меняя общий принцип работы.

## Что я оставил из черновика

Я сохранил исходные функции:

- `load_orders` читает файл с заказами;
- `get_order_status` получает статус заказа;
- `calc_revenue_by_sku` считает выручку;
- `main` запускает весь процесс.

Также оставил `pandas` для работы с таблицей и `requests` для запросов к API.
Основной расчёт тоже остался прежним: цена умножается на количество. Отменённые
заказы пропускаются, а возвраты теперь учитываются отдельно от выручки.

## Что я изменил

Вместо `print` добавил обычное логирование. Теперь в консоли видно, когда
загрузился файл, сколько в нём заказов, когда начался расчёт и почему программа
остановилась, если произошла ошибка.

При загрузке файла добавил проверки, которых не было в черновике: существует ли
файл, читается ли он, есть ли обязательные колонки и корректны ли цена,
количество и статус заказа. При проблеме скрипт выводит понятное сообщение и не
продолжает расчёт с неполными данными.

Для API добавил таймаут и три попытки запроса. После первого сбоя скрипт ждёт
одну секунду, после второго — две. Повтор выполняется только для временных
проблем: ошибки соединения, таймаута, HTTP 429 и серверных ошибок 5xx. Например,
при HTTP 404 повторять тот же запрос нет смысла.

Ещё я нашёл ошибку в расчёте. В исходном варианте, если один SKU встречался в
нескольких заказах, новое значение перезаписывало предыдущее:

```python
revenue[sku] = amount
```

Теперь сумма накапливается:

```python
revenue[sku] = revenue.get(sku, 0) + amount
```

Например, для `SKU-100` правильный результат равен `2950`, а исходный скрипт
оставлял только сумму последнего заказа — `590`.

При ручной проверке нашлась ещё одна проблема: исходник исключал только
`cancelled`, поэтому заказы со статусом `returned` попадали в результат под
названием «выручка». Я разделил показатели: фактическая выручка включает только
`delivered`, возвраты считаются отдельно, а их сумма вместе называется оборотом
до вычета возвратов.

## Как запустить проверки

Проект проверялся на Python 3.12. Зависимости:

```powershell
python -m pip install pandas openpyxl requests pytest ruff
```

Запуск тестов:

```powershell
python -m pytest -v
```

Проверка кода:

```powershell
python -m ruff check .
```

Сейчас в проекте шесть тестов. Они проверяют суммирование одинаковых SKU,
исключение отменённых заказов, отдельный учёт возвратов, ошибки в структуре
файла, нулевое количество и повторные запросы к API. Последний тест имитирует
два сбоя и успешный ответ с третьей попытки. Интернет и настоящее ожидание в
тестах не используются.

Результат последнего запуска:

```text
6 passed
All checks passed!
```

## Как я проверял расчёт

Кроме автотестов, я прогнал расчёт на предоставленном `orders.xlsx`. Статусы
брал из самой таблицы, потому что адрес API в черновике является заглушкой.

Я отдельно сверил три итоговых показателя:

```text
Фактическая выручка: 16659
Сумма возвратов: 3449
Оборот до вычета возвратов: 20108
```

Несколько значений фактической выручки по товарам:

| SKU | Сумма |
|---|---:|
| SKU-100 | 2950 |
| SKU-101 | 4800 |
| SKU-105 | 1500 |

У `SKU-105` есть один доставленный заказ на `1500` и один возврат на `1500`.
Поэтому фактическая выручка равна `1500`, а оборот до вычета возврата — `3000`.

## Ограничение

`https://api.example.com` — не настоящий API заказов, поэтому обычный запуск с
этим адресом не сможет получить статусы. Обработку успешных ответов, временных
ошибок и повторных попыток я проверяю через mock в автотестах. Для реального API
нужно будет указать рабочий адрес и, если требуется, авторизацию.
