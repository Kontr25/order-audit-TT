# Проверка заказов маркетплейса

Скрипт обрабатывает выгрузку заказов, считает показатели продаж и сверяет её с
реестром заказов и отправлений.

## Что изменено

За основу взят предоставленный черновой скрипт. Я сохранил его общую структуру
и основной расчёт `price * qty`, но добавил:

- логирование вместо `print`;
- проверку файла, обязательных колонок и значений;
- понятную обработку ошибок;
- таймаут и три попытки обращения к API с задержками 1 и 2 секунды;
- корректное суммирование повторяющихся SKU;
- отдельный учёт доставленных, возвращённых и отменённых заказов;
- сверку выгрузки и реестра по номеру заказа;
- расчёт выручки по товарам, доли возвратов и топ-5 по обороту;
- автотесты ключевой логики и граничных случаев.

## Запуск

Пути к файлам не зашиты в код и передаются аргументами командной строки:

```powershell
python order_audit.py --orders "orders.xlsx" --registry "Реестр заказов (для сверки).xlsx" --status-source file
```

Аргументы:

- `--orders` — путь к выгрузке заказов;
- `--registry` — путь к реестру;
- `--status-source file` — брать статусы из выгрузки для локального запуска;
- `--status-source api` — получать статусы через API;
- `--log-level` — уровень подробности логов, по умолчанию `INFO`.

Все доступные параметры можно посмотреть командой:

```powershell
python order_audit.py --help
```

Зависимости и проверки:

```powershell
python -m pip install pandas openpyxl requests pytest ruff
python -m pytest -q
python -m ruff check .
```

Последняя проверка: `9 passed`, замечаний Ruff нет.

## Запуск по расписанию и мониторинг

В production я бы запускал сверку один раз в день после получения обоих
файлов. На Windows для этого подошёл бы Планировщик заданий, на Linux — cron.
Использовать оба одновременно не нужно.

Например, cron-запись для запуска каждый день в 06:30 могла бы выглядеть так:

```cron
30 6 * * * cd /opt/order-audit && .venv/bin/python order_audit.py --orders /data/orders.xlsx --registry /data/registry.xlsx --status-source api --log-level INFO >> /var/log/order-audit.log 2>&1
```

В Планировщике заданий Windows я бы указал то же время, интерпретатор из
`.venv` как программу, а `order_audit.py` и его аргументы — как параметры.
Для задания настроил бы повторный запуск после сбоя, например три раза через
пять минут, запрет параллельных запусков и ограничение максимального времени
работы.

В production я бы контролировал:

- был ли успешный запуск к ожидаемому времени, его код завершения и длительность;
- появились ли оба входных файла, свежие ли они и не оказались ли пустыми;
- число заказов в каждом источнике и долю совпавших заказов;
- количество и типы расхождений: пропавшие заказы, суммы и количество;
- ошибки и время ответа API, число повторных попыток, ответы 429 и 5xx;
- выручку, сумму и долю возвратов, резкие отклонения от предыдущих периодов;
- записана ли итоговая сводка в лог и не завершился ли процесс частично.

Оповещение отправлял бы при падении задания, отсутствии свежего файла,
недоступности API после всех попыток и заметном росте расхождений или возвратов.
Конкретные пороги определил бы по накопленной статистике и требованиям бизнеса,
чтобы не создавать лишние ложные тревоги.

## Результат на предоставленных файлах

Скрипт получил следующие показатели:

- фактическая выручка: `16659`;
- сумма возвратов: `3449`;
- оборот до вычета возвратов: `20108`;
- доля возвратов: `16.67%` — 3 из 18 неотменённых заказов.

При сверке найден 21 уникальный заказ: 14 полностью совпали, в 7 есть
расхождения. Один заказ есть только в выгрузке, один — только в реестре, у пяти
отличается сумма. Расхождений по количеству нет. Для четырёх сумм вероятная
причина — в реестре записана цена одной единицы вместо полной суммы заказа.

## Как использовал ИИ

ИИ-ассистента использовал как помощника при разборе незнакомого Python-кода:
для обсуждения вариантов обработки ошибок, retry, структуры тестов и проверки
кода. Предложенные изменения просматривал по шагам, запускал локально и
проверял результат тестами. Решения по смыслу показателей и трактовке данных не
принимал только на основании ответа ИИ.

Вручную я перепроверил:

- сумму `price * qty` для нескольких заказов;
- накопление суммы, когда один SKU встречается несколько раз;
- разделение доставленных заказов, возвратов и отмен;
- итоговую выручку, сумму возвратов и оборот;
- подозрительные расхождения между выгрузкой и реестром.

Например, у `SKU-105` есть доставка на `1500` и возврат на `1500`, поэтому его
фактическая выручка равна `1500`, а оборот до вычета возврата — `3000`. Также у
`ORD-1020` вручную видно, что `610 * 3 = 1830`: вероятно, реестр содержит цену
одной единицы, а выгрузка — полную сумму заказа.

## Ограничение

Адрес `https://api.example.com` из черновика является заглушкой. Поэтому
полный локальный запуск выполняется с `--status-source file`, а работу retry и
обработку ответов API проверяют автотесты с mock. Для production потребуется
настоящий адрес API и, при необходимости, авторизация.
